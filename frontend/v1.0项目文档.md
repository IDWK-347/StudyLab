## 一、项目概述

### 1.1 项目定位

前端的目标形态是 StudyLab 的**唯一用户界面**：学生 / 教师通过浏览器完成注册登录、管理知识库文档、向知识库提问、与 AI 助手多轮对话。

Argus 的前端是一个**完成度相当高**的产品界面——35 个源文件、约 300 KB 的 Vue/TS 代码，包含营销落地页、四栏工作台、流式对话、引用溯源卡片、使用统计仪表盘。**复刻它比自己设计一个界面省力得多**，而且视觉上直接达到可演示的水准。

### 1.2 复刻范围与阶段划分

Argus 前端的 11 个页面并非都对应 StudyLab 现有或近期规划的后端能力。**页面可以一次做完，数据接入必须分期。**

| # | 页面 | 路由 | 依赖的后端能力 | 后端版本 | 前端状态 |
| --- | --- | --- | --- | --- | --- |
| 1 | 首页（营销落地页） | `/` | 无（纯静态 + 注册/登录弹窗） | — | ⛔ |
| 2 | 登录页 | `/login` | 认证 | **V1.0** | ⛔ |
| 3 | 404 | `*` | 无 | — | ⛔ |
| 4 | 系统设置（改密） | `/app/settings` | 当前用户 + 修改密码 | **V1.0** | ⛔ |
| 5 | 用户管理（管理员） | `/app/admin/users` | 管理员用户列表 / 详情 / 启停 | **V1.0** | ⛔ |
| 6 | 协作小组 | `/app/groups` | 群组 CRUD、成员、邀请、加入申请 | V1.1 | ⛔ |
| 7 | 文档管理 | `/app/documents` | 上传、解析、列表、预览、下载、软删除 | V1.2 | ⛔ |
| 8 | 知识库问答 | `/app/qa` | 混合检索 + RAG 问答 + 引用溯源（SSE） | V1.3–V1.4 | ⛔ |
| 9 | AI 助手 | `/app/assistant` | LangGraph 工作流 + 会话记忆（SSE） | V1.5 | ⛔ |
| 10 | 使用统计 | `/app/admin/metrics` | LLM 调用量 / Token / 费用统计 | **未规划** | ⛔ |
| 11 | 工作台外壳 `DefaultLayout` | `/app/*` | 无（依赖 2、4、5 的会话与角色） | **V1.0** | ⛔ |

**建议的施工顺序**：外壳（11）→ 登录（2）→ 设置（4）→ 用户管理（5）→ 首页（1）→ 404（3）。
这六项**在 V1.0 后端落地后即可端到端联调**，构成第一个可演示版本。

其余五项（6–10）可以先把**页面骨架和视觉做出来**，数据层用 mock 顶住；但**不建议**在没有后端的情况下投入——
Argus 的文档页就有一个因缺文件而编译不过的例子（见 3.3 节）。

### 1.3 V1.0 边界

**在范围内**：项目脚手架、设计令牌与视觉规范、路由与守卫、Pinia 状态管理、HTTP 客户端与鉴权拦截器、上述 6 个页面。

**明确不在范围内**：

- 任何后端接口的实现（前端只消费）
- 单元测试 / E2E 测试（Argus 前端没有任何测试，StudyLab 是否补需确认，见第 11 节）
- 国际化（Argus 界面**硬编码中文**，无 i18n 层）
- 生产部署与 Nginx（属后端 README 的阶段 7）

### 2.3 与 Argus 前端的对照

**技术上：无差异。** 前端这一层完全不受"后端是 Java 还是 Python"影响——Vue 不认识后端语言。

| 维度 | Argus 前端 | StudyLab 前端 |
| --- | --- | --- |
| axios `baseURL` | `/api` | **`/api/v1`** |

| JSON 字段命名 | camelCase | **snake_case** |
| 响应包裹 | 大部分 `ApiResponse`，**4 处例外** | **无例外**，全部 `ApiResponse` |

### 5.2 守卫与角色重定向

`beforeEach` 每次导航都 `await authStore.bootstrap()`（内部有去重，不会重复请求）：

```text
1. 公开路径 = / 、/login 、not-found
2. 已登录 + 公开路径  → 跳 authStore.homePath
3. 未登录 + 受保护路径 → 跳 /login
4. 已登录 + 受保护路径 → resolveRedirectForPath()，非 null 则跳转
```

`resolveAuthorizedPath()` 的规则：

| 条件 | 落地路径 |
| --- | --- |
| 未登录 | `/login` |
| `mustChangePassword === true` | `/app/settings`（**强制先去改密**） |
| `systemRole === 'ADMIN'` | 仅允许 `/app/admin/*` 与 `/app/settings`，其余一律踢回 `/app/admin/users` |
| `systemRole === 'USER'` | 仅允许四个业务页与 `/app/settings`，`/app/admin/*` 一律踢回 `/app/groups` |

`resolveRoleRedirect()` 在导航中执行同样的反向校验。

> ⚠️ **这是前端的一层体验优化，不是安全边界。** 后端文档（README 第 18 节安全红线）与
> `app/modules/users/permissions.py` 都写明「权限必须在服务端独立校验，不能只靠前端」。
> 前端的角色重定向**只负责不让用户看到会 403 的入口**。
>
> ⚠️ 第 3.3 节第 3 条：`meta.requireAdmin` 声明了但守卫不读。**实际生效的只有上面这套 store 逻辑。**

### 5.3 状态管理

**`stores/auth.ts`** —— 会话与角色

| 类型 | 名称 | 说明 |
| --- | --- | --- |
| state | `accessToken` | JWT access token，**只在内存**（不落 localStorage） |
| state | `currentUser` | 当前用户资料 |
| state | `isBootstrapping` | 启动恢复会话中（`App.vue` 据此显示全屏转圈） |
| state | `isAuthenticating` | 登录请求进行中 |
| getter | `isAuthenticated` | `accessToken !== null && currentUser !== null` |
| getter | `isAdmin` / `isUser` | 按 `systemRole` |
| getter | `homePath` | `resolveAuthorizedPath(currentUser)` |
| action | `bootstrap(force?)` | 有 token → `fetchCurrentUser()`，失败 → `refresh()`；无 token → 直接 `refresh()`；最终失败 → `clearSession()`。**模块级 promise 去重** |
| action | `refresh()` | 调 `refreshSession()` 换新 access token |
| action | `login(payload)` | `loginId.trim()` 后请求，成功即 `setSession()` |
| action | `logout()` | 请求失败**也要**清本地会话（`finally`） |
| action | `changePassword(payload)` | 成功后本地把 `mustChangePassword` 置 false，再拉一次当前用户 |
| action | `setSession()` / `clearSession()` | 同步维护 `http.defaults.headers.common.Authorization` |

> **access token 只存内存，不存 localStorage / sessionStorage** —— 刷新页面就靠
> refresh Cookie（`withCredentials: true`）重新换。这是合理的安全取舍，**建议照搬**。

**`stores/app.ts`** —— 群组上下文

| 类型 | 名称 | 说明 |
| --- | --- | --- |
| state | `currentGroupId` | 当前选中的群组（文档页 / 问答页 / 助手页共用） |
| state | `ownedGroups` / `joinedGroups` / `pendingInvitations` | 来自 `GET /groups/my` |
| getter | `visibleGroups` | 自有组打 `relation: 'OWNER'`，加入组打 `'MEMBER'` |
| getter | `currentGroup` / `canManageCurrentGroup` | |
| action | `applyGroupQueryResult()` | 写入集合并**自动选中** `ownedGroups[0] ?? joinedGroups[0]`；无可见组则清空 |

> ⚠️ 这个 store 依赖群组接口（V1.1）。V1.0 阶段可以先建一个**空实现**，
> 让文档页 / 问答页的"群组选择"区域显示占位，等 V1.1 再接。

#### 6.3.5 通用规则

| 情况 | 处置 |
| --- | --- |
| 简单单词换风格（`password` → `password`） | 无变化 |
| 多词驼峰（`groupId` → `group_id`） | 逐字段改名 |
| **词根也变**（`userId` → `id`、`currentUser` → `user`） | 需逐字段对照，**不能靠正则批量替换** |
| 前端内部状态（Pinia state、组件 props） | **建议保持 camelCase**（Vue/TS 惯例），只在 `src/api/` 边界做转换 |
| 转换位置 | **在 `src/api/*.ts` 里显式映射**，不要引入全局 axios 转换器——隐式转换会让类型和运行时不一致 |

> **建议：`src/api/` 层做「DTO → 前端模型」的显式映射函数**，而不是让 camelCase 的 interface 直接描述 snake_case 的响应。
> 这样后端字段变动时，改动被隔离在 `api/` 一层，页面组件不受影响。

### 6.4 响应包裹：StudyLab 无例外

Argus 前端的 `ApiResponse` 处理是**不统一的**——大部分接口包 `{success, data, message}`，但有 4 处例外：

| Argus 端点 | Argus 行为 |
| --- | --- |
| `POST /qa/ask` | 直接返回 `AskQuestionResponse` |
| `GET /assistant/sessions` | 直接返回数组 |
| `GET /assistant/sessions/{id}` | 直接返回对象 |
| `GET /assistant/sessions/{id}/context` | 直接返回对象 |

为容忍这种不一致，Argus 的 `api/document.ts` 写了一大堆防御性 normalizer：
`unwrapApiResponse()`（有 `success`+`data` 就拆）、`resolveListItems()`（依次尝试 `items` / `list` / `records`）、
`readNumber()` / `readString()` / `readNumberArray()`（宽容类型转换）。**这些一共约 150 行。**

**StudyLab 的硬性约定第 2 条是「所有响应都走 `ApiResponse`，成功和失败都是」，无例外。**
`app/common/schemas.py` 的 `ApiResponse[T]` 已实现（`ok()` / `fail()` 两个工厂方法）。

**结论：上述防御性 normalizer 可以全部删掉。** 前端只需一个通用的 `unwrapApiResponse(payload, fallback)`。
这会让 `api/` 层比 Argus 干净得多。

> ⚠️ 前提是后端**严格贯彻**这条约定。后端 `v1.0项目文档.md` 第 5.3 节自己写着
> "一旦确定，所有接口（含全局异常处理器）都必须走同一模型，否则前端要写两套解析逻辑"。
> 唯一已知的例外是 `/health`——它返回 `{success, data: null, message: null}`，**也走统一模型**，符合约定。

### 6.5 401 刷新拦截器（**需新增**）

**Argus 前端没有这一层。** 它的刷新只发生在 `bootstrap()`（应用启动 / 路由守卫）时：
有 access token 就先试 `/auth/me`，失败再 `refresh()`。

问题：**应用运行中 access token 过期（30 分钟）后，任何请求都会直接 401 失败，用户被踢回登录页**，
尽管 refresh Cookie 还有效（7 天）。

后端 `v1.0项目文档.md` 第 7.3 节明确要求补上，并特别提示了**并发陷阱**：

> ⚠️ **并发陷阱**：若同一客户端的多个请求同时收到 401 并同时触发刷新，第二个刷新请求拿的是已被吊销的旧令牌，
> 会被判定为无效并导致用户被登出。前端拦截器**必须做刷新去重**。

**需要实现的语义**：

| 项 | 要求 |
| --- | --- |
| 触发条件 | 响应 401（且不是 `/auth/refresh` 本身、不是 `/auth/login`） |
| 去重 | 同一时刻**只有一个**刷新请求在飞，其余请求排队等待其结果（与 `authStore.bootstrap` 的模块级 promise 同一套路） |
| 成功后 | 用新 access token **重放**原请求（只重放一次，避免死循环） |
| 失败后 | `clearSession()` + 跳 `/login` |
| 无限循环防护 | 重放请求若再次 401，**不再刷新**，直接失败 |

> 这是**唯一一处建议比原作做得多的地方**。理由充分：Argus 前端这个缺口在真实使用中会表现为
> "用着用着突然被登出"，而后端文档已经把要求写死了。

### 6.6 SSE 契约冲突 ⚠️

**前端的 SSE 事件名与 StudyLab 后端文档规定的对不上。** 这是一处必须拍板的冲突。

**StudyLab 后端 `README.md` 第 19 节**规定的事件：

| 事件 | data 形状 |
| --- | --- |
| `start` | `{"session_id": "..."}` |
| `delta` | `{"content": "根据"}` |
| `citation` | `{"document_id": 88, "chunk_id": 1024, "document_name": "handbook.pdf"}` |
| `done` | `{"finish_reason": "stop"}` |
| `error` | 结构化错误 |

**Argus 前端实现了两套，都与上表不同：**

| 场景 | 端点 | 事件名 | data 形状 |
| --- | --- | --- | --- |
| 问答 | `POST /qa/stream-ask` | `token` / `citations` / `evidence-overview` / `error` / `record` | `token` 是**纯文本**（非 JSON）；`citations` 是 JSON 数组 |
| 助手 | `POST /assistant/chat/stream` | `start` / `delta` / `done` / `error` | **每个事件的 data 都是完整 JSON 对象**（`AssistantChatStreamEvent`：含 `sessionId`/`toolMode`/`groupId`/`delta`/`messageId`/`reply`/`citations[]`/`error`） |

**四处具体冲突**：

| # | 冲突点 | StudyLab 后端文档 | Argus 前端 |
| --- | --- | --- | --- |
| 1 | 增量事件名 | `delta` | 助手用 `delta`，问答用 `token` |
| 2 | 增量载荷键 | `content` | 助手用 `delta`，问答用**裸文本** |
| 3 | 引用事件名 | `citation`（**单数**） | 助手在 `done` 里带全量数组，问答用 `citations`（**复数**） |
| 4 | 结束事件载荷 | `{"finish_reason": "stop"}` | 助手在 `done` 里带 `reply` + `messageId` + `citations[]` |

**两条路线：**

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| **A. 后端对齐 Argus** | 改 `README.md` 第 19 节，采用 Argus 的事件契约 | 要回写 README；但前端可照抄，且 `done` 带 `reply`+`messageId`+`citations` 比极简格式**更有用**（前端不必自己拼装） |
| **B. 前端对齐后端** | 按 README 第 19 节重写两套 SSE 解析器 | 前端要自己维护"增量拼接 + 引用累积 + 结束后定稿"的状态机；且 `finish_reason` 里没有 messageId，助手会话列表无法即时更新 |

> **倾向 A，但要作者拍板**（第 11 节第 3 项）。注意 A 路线还有一个额外好处：
> Argus 的 `done` 事件让前端可以直接用后端返回的 `messageId` 更新会话列表，不用额外拉一次接口。

**两套流式实现共用的解析骨架**（Argus 的做法，照抄即可）：

```text
fetch(url, { method:'POST', headers:{ Authorization: Bearer ... }, body, signal })
  → response.body.getReader() + TextDecoder('utf-8', { stream: true })
  → 累积到 buffer，按 '\n\n' 切分事件
  → 每个事件按行解析 'event:' / 'data:' 前缀
  → 分发给 onToken / onCitations / onError 回调
```

**不用 `EventSource` 的原因**：`EventSource` **无法自定义 `Authorization` 头**，而这里需要 Bearer token。
后端 `README.md` 第 19 节的前端示例也确认了同样的结论（用 `fetch` + `ReadableStream`）。

**中断**：`AbortController` + `signal`。助手页把中断后的半截内容保留并追加 `_(已中断)_`。

## 八、前端工程实现规格

> 第七章讲"每个页面长什么样、做什么"。本章讲"代码怎么搭"——分层、类型、组件契约、状态机。
> 本章的**组件契约逐字取自 Argus 源码**（2026-10-11 实测），其余各节是设计规格。

### 8.1 分层与依赖规则

前端分四层，**依赖方向严格单向向下**：

```text
views/          路由目标，页面编排
   ↓
components/     展示组件，靠 props / emits 通信
   ↓
stores/         全局状态（Pinia）
   ↓
api/            HTTP 调用 + DTO → 模型映射
```

| 层 | 可以做 | 禁止 |
| --- | --- | --- |
| `views/*.vue` | 组合子组件、读写 store、调用 `api/` | 直接 `fetch` / `axios`；承载大段字段转换 |
| `components/*.vue` | 展示，`props` / `emits` / `slots` 通信 | **直接调 `api/`**；直接读 store（`DefaultLayout` 这类布局组件除外） |
| `composables/*.ts` | 跨组件共享的**纯前端**状态与逻辑 | 充当 store；直接发请求 |
| `stores/*.ts` | 全局状态、会话、跨页上下文 | 直接 `axios`（唯一例外见下） |
| `api/*.ts` | HTTP 调用、映射、解包 `ApiResponse` | **`import` store 或组件** |

> ⚠️ **Argus 违反了第二条。** `LoginModal.vue`、`DocumentPreviewModal.vue`、`AccountPasswordForm.vue`
> 三个组件**直接 `import @/api/*` 并发请求**。复刻时建议改成"组件 emit 意图 → 页面调 api → 结果回传 props"，
> 否则组件既无法单独测试，也无法在别的上下文复用。

**循环依赖** —— 这是分层规则里唯一必须绕开的地方：

```text
stores/auth.ts  ──import──▶  api/auth.ts  ──import──▶  api/http.ts
                                                            │
                                          若 http.ts 为了读 access token
                                          而 import stores/auth.ts，即成环
```

Argus 的解法是**推模型**：auth store 主动把 token 写进 `http.defaults.headers.common.Authorization`，
`http` 层**从不反向依赖 store**。复刻时沿用，并让 401 拦截器也用同一招：

```ts
// api/http.ts —— 只暴露一个注册口，本身不认识任何 store
interface AuthHooks {
  getAccessToken: () => string | null
  refresh: () => Promise<string | null>   // 成功返回新 access token，失败返回 null
  onUnauthorized: () => void              // 刷新失败：清会话 + 跳登录
}
export function registerAuthHooks(hooks: AuthHooks): void
```

由 `stores/auth.ts` 在模块初始化时调用 `registerAuthHooks(...)` 注入自己。
**`api/` 层因此完全不 `import stores/`，环断开。**

### 8.2 TypeScript 类型体系

分三层。**边界清楚是这一节的全部目的。**

| 层 | 位置 | 命名风格 | 谁在用 |
| --- | --- | --- | --- |
| **DTO** | `src/api/dto/*.ts` | **`snake_case`**，逐字对应后端 | **只在 `api/mappers/` 里出现** |
| **Model** | `src/api/models/*.ts` | **`camelCase`** | 组件、store、view |
| **Mapper** | `src/api/mappers/*.ts` | — | 由 `api/*.ts` 调用 |

**为什么不让 interface 直接描述响应**：后端字段一改名（`userId` → `id` 已经发生过一次），
改动会顺着类型扩散到每一个组件。有了 mapper 这一层，改动被关在 `api/` 内部。

**Mapper 的四条实现约定**（照抄 Argus 会踩的坑）：

| 约定 | 说明 |
| --- | --- |
| 一进一出，不返回 `null` | DTO 的可选字段用 `?? 默认值` 收敛。**不要**像 Argus 的 `normalizeDocumentItem()` 那样返回 `DocumentItem \| null`，再让调用方 `.filter(Boolean)` |
| 不吞契约问题 | 字段缺失是**后端契约问题**，应当在类型层面暴露，而不是静默兜底成 `'UNKNOWN'`（Argus 的 `status: readString(...) ?? 'UNKNOWN'` 就是典型） |
| 时间字段不格式化 | 后端发 ISO 8601 字符串，**mapper 原样带过**。格式化是展示层的事，混进 mapper 会让它在测试里依赖时区 |
| 不写兼容分支 | Argus 的 `resolveListItems()` 要同时兼容 `items` / `list` / `records` 三种键名。StudyLab 后端走统一 `ApiResponse`，**不需要**这种容错 |

### 8.3 通用响应解包

后端 `app/common/schemas.py` 保证**所有**响应都是 `{success, data, message}`，所以前端只需要一个解包函数：

```ts
// src/api/http.ts
export function unwrap<T>(payload: ApiResponseDto<T>, fallback: string): T {
  if (!payload.success || payload.data === null) {
    throw new Error(payload.message ?? fallback)
  }
  return payload.data
}
```

> **这一条能省掉 Argus 大约 150 行代码**（对照见 6.4 节）。
> 前提是后端严格贯彻「所有响应都走 `ApiResponse`」——目前连 `/health` 都符合。

### 8.5 SSE 流式状态机

问答页与助手页共用同一套连接级状态机。**建议抽成 `composables/useSseStream.ts`，两侧共用。**

#### 8.5.1 连接状态

| 状态 | 含义 | 进入条件 | 离开条件 |
| --- | --- | --- | --- |
| `idle` | 未开始 | 初始 / `reset()` | 用户提交 |
| `connecting` | `fetch` 已发出，尚未收到首个事件 | 提交 | 收到首事件 / `fetch` 抛错 / 中止 |
| `streaming` | 正在接收增量 | 首个 `delta`（或 `start`） | `done` / `error` / 中止 / 流意外关闭 |
| `completed` | 正常结束 | `done` 事件 | 下次提交 |
| `aborted` | 用户主动中断 | `abort()` | 下次提交 |
| `failed` | 出错 | `error` 事件 / `fetch` 抛错 / 流关闭但**从未收到 `done`** | `retry()` / 下次提交 |

#### 8.5.2 事件 → 状态转移

以**助手页**为例（对齐 Argus 契约，即 6.6 节的 A 路线）：

| 事件 | 状态转移 | 副作用 |
| --- | --- | --- |
| `start` | `connecting` → `streaming` | 插入助手占位消息（`streaming: true`） |
| `delta` | `streaming` → `streaming` | 追加 `delta` 到占位消息的 `content` |
| `done` | `streaming` → `completed` | 用 `reply` **覆盖** `content`；写入 `messageId`；挂 `citations`；清除 `streaming`；刷新会话列表 |
| `error` | 任意 → `failed` | 置 `failed: true` + `failureMessage`；清除 `streaming` |
| 流关闭但无 `done` | `streaming` → `failed` | 兜底（防后端异常断开） |
| `abort()` | 任意 → `aborted` | 保留半截 `content`，追加 `_(已中断)_`，清除 `streaming` |

**四条实现约束**：

| # | 约束 | 理由 |
| --- | --- | --- |
| 1 | **`done` 必须覆盖而非追加** | `delta` 是尽力而为的增量；`done` 的 `reply` 才是权威全文。只追加会在丢包时留下残文 |
| 2 | **流关闭但没有 `done` 要判失败** | 后端 README 第 19 节要求"正常结束必须发 `done`"。没收到就是异常，**不能当作成功** |
| 3 | **响应性**：追加到消息数组末项时要保留该项的 Proxy 引用 | Argus 显式写了 `messages.value[messages.value.length - 1]` 而不是重新赋值整个数组——直接换数组会让流式的高频更新丢响应 |
| 4 | **必须处理 `\n\n` 跨 chunk 断裂** | 一个 SSE 事件可能被切在两个 `reader.read()` 之间。缓冲区必须**累积到 `\n\n` 才切分**，不能按单次 read 的边界切 |

#### 8.5.3 竞态与清理

| 场景 | 处置 |
| --- | --- |
| 加载历史时用户又切了会话 | 用**自增序号**守卫（Argus 的 `historyRequestSeq`）：回调里比对序号，过期结果**直接丢弃** |
| 流进行中用户切会话 / 切群组 | 先 `abort()` 当前流，再加载新上下文 |
| 流进行中组件卸载 | **`onUnmounted` 里 `abort()`** —— 否则请求泄漏、回调打到已卸载的组件上。**这一条建议在复刻时补上并确认**（Argus 的 `AbortController` 主要服务于"停止"按钮） |
| 用户在 `connecting` 阶段点了停止 | `abort()` 应能中断 `fetch` 本身（`AbortController` 对 fetch 有效，对已建流的 `reader.read()` 也有效） |

### 8.6 401 刷新拦截器

**Argus 没有这一层**（6.5 节）。它是本次复刻**唯一建议比原作做得多的部分**。

#### 8.6.1 时序

```text
用户操作        业务请求 A      业务请求 B      拦截器           后端
   │               │               │             │               │
   ├── 触发 ──────▶│               │             │               │
   │               ├───────────────┼────────────▶│               │
   │               │               │             ├── GET /documents ─▶│
   │               │               │             │◀── 401 ────────────┤
   │               │               │             │               │
   ├── 触发 ──────▶│               │             │               │
   │               │               ├────────────▶│               │
   │               │               │             ├── GET /groups ────▶│
   │               │               │             │◀── 401 ────────────┤
   │               │               │             │               │
   │               │               │      ┌──────┴──────┐        │
   │               │               │      │ 已有刷新兴  │        │
   │               │               │      │ 起？→ 入队  │        │
   │               │               │      └──────┬──────┘        │
   │               │               │             │               │
   │               │               │             ├── POST /auth/refresh ─▶│
   │               │               │             │   (带上 HttpOnly Cookie)│
   │               │               │             │◀── 200 + 新 access_token
   │               │               │             │               │
   │               │               │      ┌──────┴──────┐        │
   │               │               │      │ 广播结果给  │        │
   │               │               │      │ 所有排队者  │        │
   │               │               │      └──────┬──────┘        │
   │               │◀── 重放 A ────┼─────────────┤               │
   │               │               │◀── 重放 B ──┤               │
   │               │               │             │               │
   │               │               │             │ 刷新失败 →     │
   │               │               │             ├─ onUnauthorized()
   │               │               │             │  清会话 + 跳 /login
```

#### 8.6.2 去重状态

模块级单例，**不放 Pinia**（它是 `api/` 层的东西）：

```ts
let refreshPromise: Promise<string | null> | null = null

function ensureRefreshed(): Promise<string | null> {
  if (refreshPromise === null) {
    refreshPromise = hooks.refresh().finally(() => { refreshPromise = null })
  }
  return refreshPromise            // 并发调用者共享同一个 promise
}
```

**这与 `authStore.bootstrap()` 的模块级 `bootstrapTask` 是同一套路数**（5.3 节）。

#### 8.6.3 边界条件

| # | 情况 | 处置 |
| --- | --- | --- |
| 1 | **`/auth/refresh` 自己返回 401** | **不得**再触发刷新——否则无限递归。拦截器要按 URL 白名单跳过 |
| 2 | `/auth/login` 返回 401（密码错） | 同样跳过刷新，直接把错误抛给登录表单 |
| 3 | 重放后的请求**再次** 401 | 每个请求**只重放一次**（用 `config._retried` 标记）。第二次 401 直接 `onUnauthorized()` |
| 4 | 刷新成功后原请求的 `Authorization` 头是旧的 | 重放前**必须重新取 token**覆盖，不能复用旧 header |
| 5 | 用户主动登出时恰好有请求在飞 | `logout()` 要等/取消在飞请求，避免登出后又被刷新成"已登录" |
| 6 | 刷新失败的并发请求 | **所有排队者都要被拒绝**，不能只让第一个失败、其余悬着 |
| 7 | `mustChangePassword` 用户 | 后端可能对非改密接口统一返回 403 而非 401——**拦截器只处理 401**，403 交给页面提示 |

> ⚠️ 第 4 条尤其容易错：axios 的 `config.headers` 在重放时是**上一次的快照**。
> 必须显式重设 `Authorization`。

### 8.7 错误处理与表单校验

#### 8.7.1 后端异常 → 前端行为

后端 `app/core/exceptions.py` 的契约（已实现，实测）：

| 后端异常 | HTTP | 响应体 `message` | 前端行为 |
| --- | --- | --- | --- |
| `BusinessException` | **400** | 业务描述（后端给） | `extractApiError` 取 `message`，内联或 toast 展示 |
| `UnauthorizedException` | **401** | 业务描述 | 走 8.6 的刷新流程；刷新失败 → 跳登录 |
| `ForbiddenException` | **403** | 业务描述 | 展示 `message`，**不跳登录**（用户是登录着的，只是没权限） |
| `NotFoundException` | **404** | 业务描述 | 展示 `message`；列表页可顺带刷新 |
| `RequestValidationError` | **422** | **固定字符串** `请求参数校验失败` | ⚠️ 见下 |
| 未捕获异常 | **500** | **固定字符串** `服务器内部错误` | 展示兜底文案；**响应体不含堆栈**（堆栈只进后端日志） |
| 网络错误 / 超时 | — | 无响应体 | 用 axios 的 `error.message`（`Network Error` / `timeout of 15000ms exceeded`） |

> ⚠️ **422 不返回字段级错误。** `validation_exception_handler` 把 message 写死成
> `"请求参数校验失败"`，**不告诉你哪个字段错了**。
>
> 所以前端的表单校验**不是体验优化，而是唯一能告诉用户"哪个字段错了"的手段**。
> 这也是本文档把校验规则集中列出的原因（8.7.2）。
>
> 若希望前端能高亮具体字段，需要后端改 `validation_exception_handler` 把 `exc.errors()`
> 序列化进响应体——**这是一条对后端的改进建议，不是前端能单方面解决的**。

### 9.5 关于 CORS 与 Cookie

**开发环境走 Vite 代理，就没有 CORS 问题。** 浏览器看到的是同源请求
（`http://localhost:5173/api/v1/...` → 代理转发到 `http://localhost:8000`），
既不需要后端配 CORS，也不会有 Cookie 的 `SameSite` 麻烦。

**这一点很关键，因为 refresh token 是 HttpOnly Cookie**：跨源携带 Cookie 需要
`SameSite=None; Secure`，而 `Secure` 要求 HTTPS——**本地 HTTP 开发环境下做不到**。

**后端侧的两个缺口**（本章是前端文档，但这两条会直接卡住前端）：

| # | 缺口 | 影响 |
| --- | --- | --- |
| 1 | `app/main.py` 的模块 docstring 写着"注册 CORS 中间件"，但**代码里没有 `add_middleware(CORSMiddleware, ...)`**，只有 `RequestIdMiddleware` | 前后端**分离部署**（或前端不走代理直连 8000）时会全部请求被浏览器拦掉 |
| 2 | `Settings`（`app/core/config.py`）**没有 `cors_origins` / `frontend_url` 字段**，而 `.env.example` 第 64–65 行声明了这两个变量。由于 `model_config` 是 `extra="ignore"`，这两个值会被**静默丢弃**——不报错，也不生效 | 同上；且属于"配置声明与代码不一致" |

> **建议**：如果确定开发期一律走 Vite 代理，这两条可以推迟到生产部署时再补
> （属后端 README 阶段 7 的 Nginx 部分）。但**至少要先把 `app/main.py` 的 docstring 改掉**——
> 它现在声称做了一件没做的事。
